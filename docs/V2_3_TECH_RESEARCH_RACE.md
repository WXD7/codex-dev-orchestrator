# V2.3 开发前技术调研与有界赛马

V2.3 解决两个连续问题：人的产品意图可以确认，但技术选型可能超出人的知识边界；即使完成调研，若两三条路径都合理，文档也未必能回答真实仓库中的集成、性能、成本和恢复未知。

## 权限分工

- 人对目标、范围、非目标、风险边界、预算、是否赛马、是否允许融合和最终技术路线有最终权威。
- AI 主动扩大技术搜索、发现人未想到的框架和路径、比较证据并提出建议，但不能改写人的产品范围。
- 调研收集者、调研质检员、赛道实现者、统一评测员和意图检查员互不自批。
- 治理层无状态，不联网、不调用模型 API、不接收 API Key、不启动 Agent，也不持有任务或 worktree。

## 四路调研门禁

`compile_technology_research()` 编译外部研究 Agent/浏览器提交的冻结证据。默认要求：

1. 至少两个独立社区域名，且至少一个近三年的真实使用信号；
2. 至少两项学术来源，且至少一项近五年同行评审研究；十年以上论文只有在标明基础性并被近期研究佐证时可用；
3. 至少两个开源框架，每个同时引用官方仓库和官方文档；
4. 每个框架完整评估需求适配、成熟度、维护、安全、集成、扩展、生态和许可证；
5. 至少两条可行技术路径，每条写明假设、优势、风险、工作量和无法只靠文档消除的未知；
6. 全新只读调研质检员只看冻结证据包，不看收集 transcript 或候选实现。

任何来源缺少主张或局限、推荐缺少来源链和权衡、框架只列优点、质检员自我复核，都会生成阻塞项。通过后得到不可变 `research_hash`。

## 人确认技术策略

`compile_intent_brief()` 现在要求通过质检的 `technology_research` 和人的 `technology_strategy`。高影响技术选择必须绑定同一 `research_hash`。

`single_path` 必须且只能选择一条研究路径并记录人的理由。`bounded_race` 必须满足：

- 选择 2–3 条存在真实经验未知的路径；
- 调研证据明确说明赛马必要性；
- 冻结共同测试命令、评估维度、总时间预算、成本预算、停止条件；
- 明确赛后是否允许融合。

这些字段形成 `technology_strategy_hash`，并与 research/intent/inspection/contract/plan/external task 一起进入可信控制器 HMAC 意图签署。签署前不得创建任何实现任务。

## 隔离赛马与统一评测

启用赛马时，验证计划在环境预检后插入：

```text
parallel_technology_race
  → race_evaluation
  → race_human_selection
  → owner_implementation
```

每条赛道必须证明唯一 context/worktree、相同 contract/research/strategy、相同冻结数据、测试和评估维度、预算内完成、无外部动作、提交前互不可见。正常退出或“我完成了”的文字不算证据。

统一赛马评测员使用全新只读上下文，看到候选产物和 Diff，但看不到赛道 transcript 或同伴结论。它必须对每条路径使用相同测试哈希和评估维度，只能输出：

- `keep_path`：建议保留一条合格路径；
- `fuse_paths`：在预先允许融合时，说明要吸收的明确优点；
- `reject_all`：全部不合格。

评测建议不产生路线权力。

## 第二次人类裁决

`attest_race_selection()` 由可信控制器把人的决定绑定 `evaluation_hash` 和原外部任务，不进入 MCP：

- 保留一路时，主实现必须继续该赛道原 context，避免重新交接损失；
- 融合时，必须创建不同于所有候选赛道的新 integration owner，并列出要融合的具体优点；
- 全部不合格时，ledger 停在 `needs_human_decision`，主实现阶段无法启动。

这样赛马不是“多开几个 Agent 看谁说得好”，而是一个有预算、有可比实验、有独立评测、最终由人授权的经验性技术决策协议。

## 可视化投影

`delivery_handoff()` 提供中文短名和实时状态字段，供 Kandev/LobeHub 现有任务页投影：

- 技术调研员；
- 调研质检员；
- 技术赛道一 / 二 / 三；
- 统一赛马评测员；
- 技术路线裁决；
- 人类选路后才出现可创建的主实现者。

每项显示 `execution_state`、`progress_summary`、`current_difficulty`、`dependency`、`needs_human` 和心跳；执行状态与交付裁决保持分离，不建立第二套任务数据库。
