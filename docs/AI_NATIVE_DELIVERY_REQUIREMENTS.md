# AI 原生交付系统：产品与质量需求

## 产品目标

把一个研发目标可靠地推进到可审查交付物。人在方向、利害关系、审美体验、歧义、政策、不可逆动作和最终责任节点做判断；其余可由确定性程序或 AI 更稳定判断的事项自动完成。

成功不是“启动了很多 Agent”，而是：

- 需求和验收没有在执行过程中静默漂移；
- 交付质量不低于一个强 Codex 连续完成的基线；
- 多上下文只在有独立边际价值时启用；
- 人不需要持续看终端，系统会在真正需要决定时带着证据找人；
- 中断、额度不足、工具失败和检查失败都能说明原因并安全恢复；
- 每次自动决策都能追溯到契约、风险、证据和策略版本。

## 非目标

- 模仿一个人类公司的岗位和开会过程；
- 所有任务都强制多 Agent；
- 用 LLM 替代编译、测试、扫描器或版本控制；
- 重新开发 LobeHub、Kandev、Symphony、Spec Kit 或 GitHub Actions；
- 自动获得合并、部署、购买用量或其他真实世界权力；
- 根据账号价格或猜测伪造精确剩余额度；
- 让发现问题的监察者直接修改并隐藏问题。

## 必需能力

### 开工前

1. 技术确认前默认执行四路调研：社区真实使用讨论、近期高质量学术研究、至少两个维护中的开源框架、官方文档/标准/一手资料。逐来源记录日期、方法、主张、质量信号和局限；逐框架比较需求适配、成熟度、维护、安全、集成、扩展、生态和许可证。
2. 全新只读调研质检员必须只看冻结证据包，阻断来源单一、陈旧论文无近期佐证、只列一个框架、适配矩阵缺项、自我质检和选择偏差。AI 可扩大技术搜索，但不能改写人确认的目标、范围、非目标和风险边界。
3. 由意图确认员主动暴露用户、场景、最终结果、开发执行器、产品运行时、技术选择理由、具体输入/输出验收样例、非目标、禁止行为和关键风险缺口。
4. 当 2–3 条技术路径都可行且存在文档无法消除的真实未知时，AI 可建议赛马；人确认是否赛马、候选路径、统一数据/测试/评估维度、时间/成本预算、停止条件和融合权限。没有真实未知性不得为多 Agent 而赛马，赛道不得超过三条。
5. 全新只读意图检查员必须逐项对照原始对话、冻结调研、意图简报、拟定契约和验收样例，阻断目标偷换、遗漏、供应商混淆、未确认默认和验收不可证明。
6. 用 research/strategy/intent/inspection 哈希绑定本次契约；变更任一项必须形成新哈希和决策记录。人类签署绑定 research/strategy/intent/inspection/contract/plan/external task 前不得创建实现任务。
7. 区分产品需求、技术方案和执行任务。
8. 在代码修改前确认需要人决定的架构、安全、数据、成本和体验问题。
9. 把不确定性分为政策选择、领域事实、工程不变量和可研究事实；只向人追问前两类中的真正阻塞项。
10. 生成环境 capsule，验证 cwd、真实 Diff 根、权限、PATH、端口和锁；预检失败不得启动 owner。
11. 每个关键问题必须有稳定决策 ID、关联验收、影响、后果、建议默认、决策人、可逆性和答案；只有高影响且不可安全默认的问题阻塞。
12. 人类答案必须形成新契约 delta，并由可信控制器签名绑定父契约、新契约、新计划和同一外部任务；未完成 attestation 不得创建 owner。

### 执行中

1. 默认一个连续 owner 上下文，避免无谓交接损耗。
2. 写操作位于隔离 worktree，凭据和权限最小化。
3. 按失败模式动态选择检查，不按岗位名拆分。
4. 限制并发、时间、Token、额度和自动返修次数。
5. 记录命令、Diff、测试、扫描、工具失败、模型使用量和停止原因。
6. 每个阶段只由可验证产物不变量推进；Agent 自述和进程正常退出没有状态权。
7. 检查点必须原子写入、单写者、可签名 replay；中断恢复不得重复已完成的有副作用步骤。
8. 每个 Agent 必须使用中文短名，并持续报告使命、执行状态、进展、当前困难、依赖、人工需要、来源 task/session、校准模式和心跳。
9. 监控视图必须按唯一 Agent 计数，区分“执行状态”和“交付裁决”，并复用 Kandev/LobeHub 的任务页面而不是建立第二事实源。
10. 技术赛道必须使用唯一上下文和隔离 worktree，面对同一冻结契约、数据、测试、评估维度和预算；提交前互不可见，任何路径不得执行外部动作。
11. 统一赛马评测员必须是全新只读上下文，看候选产物和 Diff 但不看赛道 transcript；它只能建议保留一路、融合明确优点或全部不合格。最终技术路线由人绑定 evaluation hash 决定；保留路径继续原上下文，融合使用新的明确 integration owner，全部失败停止。

### 验证

1. 确定性 CI 先于语义判断。
2. 普通代码默认使用契约/领域语义、状态/信任边界、测试预言机三条正交监察；安全、数据兼容、E2E/UX、可靠性/成本和对抗性检查按风险扩展。
3. 监察上下文彼此独立、只读，并在提交前看不到其他结论。
4. 高风险发现必须说明本次引入、证据和复现；低于 0.80 置信度不阻塞。
5. 测试生成与测试有效性判断分离。
6. Test healer 不得跳过测试、弱化断言或把产品缺陷改成测试通过。
7. 高风险交付可以把属性测试、mutation test 和真实浏览器 E2E 声明为必需证据类别；缺失等同失败。
8. Inspector 必须提交结构化复现包；跨通道同根因只生成一个返修项，同时保留各通道贡献。
9. 新增或实质变更的 Inspector 默认 shadow；只有在人工标注 Good/Bad Case 上同时满足召回率、误报率、人机一致率、样本量和独立贡献阈值，才获得 blocking 资格。
10. Bad Case 只有在人工/专家确认且有复现证据后才能进入隐藏 must-kill registry；禁止 Agent 自动晋级自己的发现。

### 收敛与交付

1. 聚合器去重并生成一次合并返修包。
2. 原 owner 在原上下文完成返修，随后重新运行完整验证计划。
3. 第二次不收敛、存在高风险争议或权限不足时交给人。
4. 最终状态只能是“可以交给人合并/发布”，不能自我批准。
5. 上线型任务同时需要回滚、兼容性、可观测性、安全、性能和成本证据。
6. 全量复验后必须由全新只读上下文盲审；它看不到 owner 对话和先前发现，并逐一验证 must-kill 反例。
7. 盲审失败不再自动返修，诚实停在人工决定。
8. 最终人工交接必须提供 Review Packet：签名证据哈希、阶段结果、Agent 进展/困难、shadow 与 blocking 发现摘要、停止原因和仍由人决定的事项。

## 人类决策点

默认保留：

- 模糊或相互冲突的需求；
- 重大架构与技术路线；
- 安全、隐私、权限和法律政策；
- 数据删除、迁移和不可逆动作；
- 外部通信、付费、额度购买、发布与部署；
- UI 审美和最终体验；
- 高风险证据争议；
- 最终合并或发布。

低风险代码风格、确定性检查结果、可复现缺陷和明确规则符合性不需要人逐项判断。

## 系统自身的验收指标

- 首轮通过率与每任务返修次数；
- AI 发现的确认率、误报率和线上漏出率；
- 每条监察通道的独立真实缺陷贡献；
- 通道间重合率和被裁决过滤比例；
- flaky test 比例和 healer 弱化测试事件数；
- 每个确认缺陷的 Token、时间和费用；
- 单 Agent 与多 Agent 在同类任务上的质量/成本差异；
- 人工介入次数、原因和平均等待时间；
- 中断恢复率与重复执行比例；
- 未经授权的写操作、权限绕过和外部副作用必须为零。

新通道先以影子模式运行。只有准确率和独立贡献稳定后才成为阻塞门禁；长期没有边际价值的通道应降频、合并或关闭。
