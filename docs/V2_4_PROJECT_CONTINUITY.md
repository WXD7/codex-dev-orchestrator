# V2.4 项目连续性与隔离

## 目标

让任意全新 Codex 对话在没有旧会话历史时，仍能从一个明确的 Git 项目
恢复当前目标、边界、证据和下一步；同时不把其他项目的业务事实带进来。

## 五层机制

1. **纯路由入口**：工作区根只选择项目。人或当前 Git 根必须唯一确定目标；不用对话新旧、UI 最近记录或目录顺序猜测。
2. **项目硬绑定**：`takeover` 要求精确 Git 根，验证 `project_id`、分支、基线和可选 remote。
3. **唯一当前状态**：每个项目只使用自己的 `.ai-delivery/CURRENT_STATE.json` 作为恢复点。历史报告必须带 superseded marker，不能冒充当前任务。
4. **证据封口**：`EVIDENCE_INDEX.json` 用 SHA-256 绑定每个必读来源。只允许项目内相对路径；重复、越界、缺失、未索引或哈希漂移都阻断接管。
5. **冷启动验收**：项目自己声明无历史驾驶员必须能回答的事实和不得执行的动作。单元测试验证机械边界，真实只读新会话验证模型是否能正确接管。

## 可以与不可以跨项目的信息

| 可进入全局治理层 | 必须留在项目内 |
| --- | --- |
| 通用治理算法与安全门 | 产品需求、范围和当前决策 |
| 已匿名的失败模式 | 领域事实、客户或案例材料 |
| 通用评测方法、证据格式 | Prompt、预期答案、金标和 Bad Case 载荷 |
| 驾驶员自身的路由/隔离/观测改进 | 供应商活跃选择、凭据、账务和运行状态 |

现有治理仓库中的领域示例只是非运行时测试 fixture，不进入任何其他
项目的 `required_read_order`，不能被驾驶员当作新项目的默认需求。

## 边界和剩余风险

- SHA-256 证明文件没有在索引后漂移，不证明写入者身份或业务真实性；高风险修改仍需独立复验。
- 工作树未提交修改会警告而不会被覆盖，因为它们可能是上一位 owner 的当前开发。
- 用户主动把 A 项目材料粘贴到 B 项目仍然是新输入；系统会标记冲突，但不能在不理解语义的情况下证明它一定属于别的项目。
- 在工作区之外启动且没有指定项目的对话不会自动得到产品上下文；这是有意的安全失败，应由人选择目标。
