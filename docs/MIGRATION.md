# 从旧编排台迁移

## 为什么迁移

旧版把看板、任务数据库、固定角色、worktree、Agent 执行、消息和审批全部放在一个 Python 服务中。这便于验证概念，但会与 LobeHub、Kandev、Symphony、Spec Kit 和 GitHub Actions重复，并把注意力消耗在 UI 和基础设施上。

新架构保留有价值的不变量：

- 本地订阅 CLI，不接模型 API；
- worktree 隔离；
- 只读评审不修代码；
- 结构化结果和证据；
- 不自动 push、merge、deploy；
- 额度不足不伪装为代码失败；
- 人类关键门禁。

但这些保证由最合适的组件分别持有，本仓库只保留跨组件治理策略。

## 阶段

### 阶段 1：影子治理

- 旧任务继续运行；
- 同一任务额外生成工作契约和验证计划；
- 新裁决只报告，不阻塞；
- 比较新旧流程的缺陷、返修、时间和 Token。

### 阶段 2：成熟控制平面接管执行

- LobeHub 接管人类入口；
- Kandev 接管研发任务、worktree 和 review；
- 需要长时间工单轮询时启用 Symphony；
- GitHub Actions 接管确定性 CI；
- 旧 Python 看板改为只读迁移视图。

### 阶段 3：治理门禁启用

- 契约未就绪不能进入写阶段；
- 只有准确率稳定的监察通道可以阻塞；
- 一次返修规则生效；
- 高风险与最终动作进入 LobeHub 人类收件箱。

### 阶段 4：旧运行时退役

只有在以下证据齐备后才能单独批准删除：

- 历史任务和审计工件已导出；
- 新控制平面连续完成代表性任务；
- 中断恢复、权限、额度和 CI 已验证；
- 新旧基准显示质量不降低；
- 明确的回滚方案存在。

本分支不会自动删除 SQLite、旧 worktree、分支或历史记录。

## 代表性验证任务

德国法律计费 Demo 适合作为高风险验证：它同时包含需求澄清、法源与时间有效性、金额计算、拒绝臆测、数据来源、自动测试、UI/E2E 和最终人类体验判断。

它必须使用预先固定的验收契约，不能为了让新工作流看起来成功而修改成功标准。相同任务还应以单 Codex 基线运行，用事实判断多维监察是否带来净价值。
